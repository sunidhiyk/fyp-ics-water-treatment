# Evaluation Results (Phase 7)

Generated by `python -m eval.evaluate` on `data/run1` (510 s of operation: normal
traffic plus five 45-second attack episodes). Evaluation unit is one second
(tick); ground truth is the device log's per-tick label. Reproduce with:

```bash
python -m net.generate_dataset --out-dir data/run1 --speedup 0 --seed 42   # dataset
python -m detect.lstm.train --device-log data/run1/device_log.csv
python -m eval.evaluate
```

## Ablation — per-second precision / recall / FPR / F1

| Layer | Precision | Recall | FPR | F1 |
|---|---|---|---|---|
| DPI (rule) | 1.000 | 0.600 | 0.000 | 0.750 |
| NetFlow | 1.000 | 0.200 | 0.000 | 0.333 |
| LSTM | 0.833 | 0.600 | 0.095 | 0.698 |
| **Combined** | **0.893** | **1.000** | **0.095** | **0.943** |

No single layer sees more than 60% of the attack seconds. Combined, the three
layers flag every attack second (recall 1.000). The combined false-positive rate
comes entirely from the LSTM's sliding window running past the end of an attack
(see the notes below).

## Per-attack-class recall

| Layer | FDI | Command inj. | Flooding | Replay | Stealth |
|---|---|---|---|---|---|
| DPI (rule) | 100% | 100% | 0% | 100% | 0% |
| NetFlow | 0% | 0% | 100% | 0% | 0% |
| LSTM | 100% | 100% | 0% | 0% | 100% |
| **Combined** | **100%** | **100%** | **100%** | **100%** | **100%** |

Every attack class is covered by at least one layer, and each layer's blind spots
are covered by another:

- **Flooding** is a burst of valid reads that changes nothing in the process, so
  neither DPI (which inspects writes) nor the LSTM (which watches the process) can
  see it; the NetFlow volume monitor catches it.
- **Stealth** is a protocol-valid command from the authorised HMI address, so DPI
  cannot flag it; the LSTM catches the abnormal process behaviour it causes.
- **Replay** re-sends the controller's most recent legitimate command. That
  command already matches what the controller wants, so the process behaves
  normally and the LSTM sees nothing; DPI catches it because it comes from an
  unauthorised source. (Replaying an old, out-of-context command would disturb
  the process; this scenario does not test that.)

|---|---|---|---|---|---|

| NetFlow | missed | missed | 0 | missed | missed |

The combined system raises an alert in the first second of every attack episode.

## Notes on the numbers

- **Where the false positives are.** All 27 false-positive seconds (FPR 0.095)
  are LSTM alerts in the 1–9 seconds immediately after the false-data-injection,
  command-injection and stealth episodes end (9 after each). The LSTM scores
  10-second windows, and a window ending up to 9 s after an attack still contains
  attack seconds. The strict per-second ground truth labels those seconds normal.
  The LSTM raises no alerts anywhere else in normal operation, and DPI and
  NetFlow have a 0% false-positive rate. A deployment could suppress this tail
  or report the LSTM's alert time as the start of the window.
- **Earlier numbers were affected by a data bug.** A previous version of these
  results (recall 0.911, precision 0.958, stealth recall 56%) came from a dataset
  in which the legitimate controller only sent a command when its own decision
  changed. After the command-injection and stealth attacks it therefore never
  switched the affected pump back, so seconds labelled normal after those attacks
  still carried the attack's effect, and the LSTM was partly trained on them. The
  controller now re-applies its outputs every cycle, as a PLC does, and a test
  (`tests/test_dataset_generator.py`) checks that pumps are restored once an
  attack ends. All numbers above come from the corrected dataset.
- **These are simulator results.** They show the layers work as designed on the
  attacks and operating conditions they were built for. On the public HAI dataset
  the LSTM layer does not generalise well; see [hai_validation.md](hai_validation.md).
